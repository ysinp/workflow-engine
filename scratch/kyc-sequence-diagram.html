KYC onboarding sequence

How the customer and compliance reviewer journeys map onto actual UI screens and service calls, for the Secure Onboarding KYC proof of concept. Each Note marks which screen the user is looking at when that step happens.

Customer-facing path Reviewer-facing path

1. Sign-up through risk decision

One submission, one of two outcomes. A LOW risk score resolves in seconds with no human involved; a HIGH score hands the case to a reviewer, and the customer's own screen updates live the moment a decision is made — no refresh, no second visit.

    participant Accounts as create-account

    Customer->>UI: Complete KYC wizard, submit
    UI->>Submission: POST /api/account-submissions

    Submission->>Accounts: stage application, hash password
    Accounts-->>Submission: applicationId
    Submission->>Orchestration: POST /workflows/account-creation/executions
    Orchestration->>Temporal: WorkflowClient.start(...)

    Orchestration-->>Submission: 202 Accepted
    Submission-->>UI: submissionId, status RUNNING

    Note over UI: inline status panel, polling every second

    Temporal->>Orchestration: dispatch workflow task
    Orchestration->>Risk: evaluateRisk(KYC data)

    alt LOW risk
        Orchestration->>Accounts: activateAccount
        Accounts-->>Orchestration: account created
        Orchestration->>Temporal: complete execution - APPROVED
        UI->>Submission: GET status (poll)
        Submission-->>UI: COMPLETED, APPROVED

        Customer->>UI: Sign In

    else HIGH risk
        Orchestration->>Temporal: Workflow.await(review decision)
        Note over Temporal: suspended - zero cost while waiting
        UI->>Submission: GET status (poll)
        Submission-->>UI: AWAITING_REVIEW
        Note over UI: result screen - under review

        Reviewer->>UI: Sign In
        UI->>Accounts: POST /api/accounts/signin
        Accounts-->>UI: JWT, role REVIEWER
        Note over UI: Dashboard / Review Console
        UI->>Orchestration: GET /executions/awaiting-review
        Orchestration-->>UI: pending cases
        Reviewer->>UI: Open case, approve or reject
        UI->>Submission: POST .../decision
        Submission->>Orchestration: forward decision
        Orchestration->>Temporal: signal submitReviewDecision
        Temporal->>Orchestration: resume workflow
        Orchestration->>Accounts: activateAccount or rejectApplication
        Accounts-->>Orchestration: done
        Orchestration->>Temporal: complete execution - APPROVED or REJECTED
        UI->>Submission: GET status (poll, customer's own tab)
        Submission-->>UI: COMPLETED
        Note over UI: customer's screen updates live, no refresh
    end

2. How one status poll resolves

There is no push channel anywhere in this system — submissionId is literally the Temporal workflow ID, renamed at the API boundary, and every "live" update is a poll that asks the Server what is true right now. describe() and query() are reads: no Activity runs and no Event is appended to the workflow's history. 

sequenceDiagram
    participant UI as React Frontend
    participant Submission as account-creation-submission
    participant Orchestration as orchestration engine
    participant Temporal as Temporal Server

    Note over UI: SignUp.tsx - setInterval(poll, 1000ms)
    UI->>Submission: GET /api/account-submissions/{submissionId}
    Submission->>Orchestration: Feign GET /executions/{workflowId}
    Note over Submission,Orchestration: submissionId and workflowId are the same string
    Orchestration->>Temporal: stub.describe()
    Temporal-->>Orchestration: RUNNING, COMPLETED, or FAILED

    opt status is RUNNING
        Orchestration->>Temporal: stub.query("isAwaitingReview")
        Temporal-->>Orchestration: true or false
        opt awaiting review
            Orchestration->>Temporal: stub.query("getPendingRiskAssessment")
            Temporal-->>Orchestration: risk level, score, reasons
        end
    end

    Orchestration-->>Submission: status + result
    Submission-->>UI: SubmissionStatusResponse
    Note over UI: setPollStatus(...) / setRiskPhase(...) - screen re-renders

Two independent loops read the same execution this way: the customer's tab every 1s, the reviewer's queue every 8s. When a reviewer submits a decision, nothing is sent to the customer's browser — their next poll simply lands after the Signal was processed and describe() now returns COMPLETED. "Live" means "polled often enough to feel live", not a websocket.

3. Reviewer: saving a diagram in the Workflow Editor

A separate, design-time capability on the same UI: the reviewer's canvas round-trips through Postgres instead of browser storage, so a diagram survives a reload or a different reviewer opening the page. 

sequenceDiagram
    actor Reviewer
    participant UI as Workflow Editor
    participant Orchestration as orchestration engine
    participant DB as PostgreSQL

    Note over UI: Workflow Editor page loads
    UI->>Orchestration: GET /api/workflow-definitions/{name}
    Orchestration->>DB: select by name
    DB-->>Orchestration: saved diagram, or none found
    Orchestration-->>UI: diagram JSON, or 404
    Note over UI: canvas renders initialNodes / initialEdges

    Reviewer->>UI: Edit diagram, click Save
    UI->>Orchestration: POST /api/workflow-definitions
    Orchestration->>DB: upsert by name
    DB-->>Orchestration: saved
    Orchestration-->>UI: 200 OK
    Note over UI: save confirmation shown on canvas
